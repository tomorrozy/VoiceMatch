# 设计文档：VoiceMatch —— 「你最像哪位歌手」

- 状态：待确认（v0.2，已回应构建者审阅）
- 日期：2026-11-18
- 路线：C（自监督嵌入 + 可解释声学特征 + 人类盲听校准）

> v0.1 → v0.2 的主要修正：把「评估集是谁」写死为真实业余录音（库内留出只做管线自检）；重定义标注任务，使 Top-K 可计算；两侧预处理改为严格对称（分离开关也对称）；v1 冻结嵌入底座、只训校准层；分位参照池限定同性别；补输入契约、拒答分母与采集通道约束。

---

## 1. 意图

用户录一段清唱，系统从**音色、音高、共鸣、唱腔**四个维度把他和一批歌手做比对，输出「你最像谁」以及一份能解释「为什么像」的报告。

第一版要验证的是**准**，不是传播。因此所有取舍服从一个原则：**准确度必须可度量、可复现、可证伪**。任何无法被基准集检验的功能都不进 MVP。

判断「像不像」的权威是人类听觉，不是余弦相似度。校准层（把模型分数对齐到人的感知）是本项目的核心，不是附属模块。

## 2. 目标 / 非目标 / 反目标

### 目标

- **G1 与人类感知一致**（北极星）：在**真实业余录音**构成的评估集上，被受理查询的 Top-3 命中率 ≥ 65%（基准集跑完后定死具体数）。**同时必须报告受理率**，且受理率 ≥ 85%——否则系统可以靠大量拒答刷命中率。
- **G2 可解释**：四维各有分数与图表，能看到「音色像 A、唱法像 B」的依据；每个维度分数是**该用户在同性别歌手池中的分位**，不是黑箱绝对数。
- **G3 稳定**：同一人同一采集通道、换设备换遍数，Top-3 重合 ≥ 2/3。
- **G4 可复现**：同音频 + 同模型/库/校准版本，输出逐字节一致；结果写入三个版本号。
- **G5 会拒答**：质量不达标时返回结构化拒答原因，不硬给结果。

### 非目标

- 实时变声、AI 翻唱、RVC 类语音克隆
- 通用声纹识别 / 身份验证
- 整首歌的卡拉 OK 评分
- 付费、会员、社区、裂变链路（报告页做成可截图静态页即可）
- 唱歌能力评价

### 反目标（技术跑通也算失败）

- 同一段音频两次运行结果不同
- 换个手机结果全变
- 用户看到结果第一反应是「离谱」
- 必须唱完整首歌才能出结果
- 报告只有结论、无可核对依据
- 靠高拒答率换取好看的命中率

## 3. 约束

- **版权**：全链路只用清唱/无伴奏。歌手侧素材仅作内部分析，不对外分发原唱片段；对外只呈现歌手名与相似度。
- **隐私**：声音属敏感个人信息（《个人信息保护法》）。单独同意、明示用途、支持删除、加密存储、最短保留期。
- **训练用途分离**：默认情况下，用户上传与标注数据**只用于评估，不用于训练**。校准层优先用库内配对数据训练（见 5.4）。若取得二次授权，再纳入真实数据——这不让项目卡住。
- **成本**：MVP 允许 CPU 推理与离线批处理；全库特征与嵌入离线预计算，线上只算用户侧。
- **关键路径**：真人采集与标注 3–4 周（含招募与同意流程），最长的链，先启动。

## 4. 路线选择

| 路线 | 做法 | 结论 |
|---|---|---|
| A 手工声学特征 | f0、共振峰、谱倾斜、HNR、颤音率等，规则加权 | 否。可解释性最好，但唱腔覆盖不了，泛化弱，天花板低 |
| B 自监督嵌入（完整训练） | wav2vec2/HuBERT + ArcFace/triplet 训练投影头 | 否（v1）。25 位歌手按歌手切分后每折类别太少，训不动也验不了 |
| **C 混合 + 感知校准** | 冻结的自监督底座提供相似性，手工特征提供解释，盲听数据校准排序 | **采纳** |

**v1 的关键取舍：不训练嵌入，只训练校准层。** 冻结的 wav2vec2/HuBERT 底座在中层已含相当强的音色与韵律信息，先用它建立基线；校准层参数少、样本需求低、可解释、可回滚。等库与标注规模上来、且看得到瓶颈，再考虑微调底座——那是 v2 的事，不进 v1 计划。

## 5. 系统设计

### 5.1 统一预处理管线（严格对称）

准确性最容易漏水的地方：若歌手侧是录音棚、用户侧是手机房间，系统比的是**制作与设备**，不是嗓音。

两侧走同一条管线、同一组参数：

1. 解码 → 单声道 → 24 kHz
2. VAD 截取有效发声段，去首尾静音
3. 人声分离开关**两侧一致**：要么都跑同一分离模型，要么都不跑。不允许一侧分离、一侧不分离——分离伪影会制造假相似
4. 响度归一化到统一 LUFS 目标
5. 去混响（WPE 类，两侧同开同关）
6. 限幅

**契约测试（进 CI）**：同一输入下，两侧的重采样率、分离开关状态、归一化后 LUFS、分析窗长/帧移、去混响开关必须逐项相等。管线一改，测试即红。

### 5.2 特征层（可解释的那一半）

| 维度 | 提取 | 派生指标 |
|---|---|---|
| 音高 | CREPE 或 pYIN，帧级 f0 + 有声概率 | 中位音高、音域跨度、f0 抖动稳定性 |
| 音色 | MFCC、谱对比度、LTAS 谱倾斜、谱质心 | 明亮度、厚度、气声感 |
| 共鸣 | LPC 共振峰 F1–F3、低频能量占比、HNR | 胸腔/口腔/头腔倾向 |
| 唱腔 | 颤音率与幅度（cent）、滑音/连音比例、起音硬度、气声比例 | 颤音型、直音型、断句习惯 |

- 每个维度输出**同性别歌手池中的分位（0–100）**，不输出原始物理量。
- **风格（流行/民谣/摇滚）只作展示标签，不进分位计算池**。原因：MVP 库的格位太稀疏（见 6.2），按风格切池后每格不足 2 人，分位退化成名次，跨设备重录就会跳档，与 G3 冲突。

### 5.3 嵌入层

- 底座：wav2vec2 / HuBERT / WavLM 中间层帧级表征，**v1 冻结，不训练**
- 池化：注意力池化，或 mean+std 拼接
- 输出 L2 归一化的片段向量，余弦作为相似性初值
- 歌手原型向量 = 该歌手全部片段向量的（加权）质心
- 若后续微调：投影头 + ArcFace，**交叉验证按歌手切分**

### 5.4 校准层（核心）

- 训练数据：**库内配对**——同歌手**不同录音**（不同歌曲/场次）为正，不同歌手为负；同一份录音切出的两段不构成正对。这是 R29 的硬约束，构建期会告警、`--strict-pairs` 会拒绝，细节见 `docs/2026-11-19-calibration-pairing-constraint.md`；不依赖真实用户数据即可起步
- 模型：Bradley-Terry / RankNet，输入 = 嵌入余弦 + 四维特征差，输出 = 感知相似度
- 真实标注作为**评估集**，也可在取得二次授权后转为训练集
- 报告中的百分比来自校准后分数；原始余弦只进日志
- 归因：能给出「主要因为音色接近 / 主要因为颤音模式接近」

### 5.5 歌手库

- 规模：MVP 20–30 位，男女各半，覆盖流行/民谣/摇滚/R&B 与高音/中低音
- 每人 5 首，studio 与 live 目标 3:2。**若 live 无法获得干净无伴奏母版，则全库退化为 studio**，并把「live 缺失」记为已知偏差写进结果说明。**至少 2 首必须能产出有效窗口**（R29：单份录音的歌手无法提供跨录音正对）
- **不给歌手手工精挑乐句**：库内片段与用户片段用**同一条自动选窗规则**（持续有声、音高稳定、能量充足）切出 8–12 秒。人工精挑是"好看"和用户"随手一段"之间的不对称，会直接抬高 G1 分数而不可迁移
- 库版本化；特征与嵌入离线预计算并缓存

### 5.6 输入契约

- 有效发声 ≥ 8 秒，总时长上限 60 秒
- 纯清唱 → 直接进管线；**带伴奏的跟唱 → 强制走分离**（与库同构），并记为该查询的元数据
- 取窗：自动，优先音高稳定且能量充足的连续段；用户不能指定
- 质量门限（拒答）：有效发声时长不足、SNR 过低、削波严重、音高检测有声比例过低

### 5.7 采集通道（决定 G3 能否验收）

- v1 **只支持一个通道**：浏览器 `getUserMedia`，显式关闭 AGC、降噪、回声消除，请求固定采样率
- iOS Safari 的后处理不可控 → v1 若必须覆盖 iOS，则该设备组的 G3 单独验收并标注局限
- G3 只在**同一通道内**验收；跨通道（不同浏览器/设备）作为已知局限，不承诺

### 5.8 服务

- 异步任务：上传 → 预处理 → 特征+嵌入 → 校准打分 → 报告 JSON
- 幂等：按音频内容哈希缓存
- 结果写入模型/库/校准三个版本号
- 拒答路径结构化，不进入打分

## 6. 验收

### 6.1 评估集必须是谁

**必须是真实业余清唱**，因为产品承诺是「我最像谁」，而库里的人是职业歌手。用库内留出录音当 query，测的是**闭集歌手识别**，与承诺不对应，且校准出的映射不迁移到手机前的普通人。

- 采集规模：60–100 位普通人 × 3 段（不同场景/设备），得到 180–300 条 query
- 每份录音带同意书（评估用途；训练用途单独勾选）
- **库内留出配对只作阶段 0 的管线自检**，不进 G1 口径，报告里必须标为"代理指标"

### 6.2 标注任务（保证 Top-K 可计算）

- 候选集构造：每条 query 由系统取 **Top-3 + 5 位随机歌手（同性别）** 共 8 位，打乱顺序展示
- 标注者任务：从 8 位里选「最像的 1–2 位」，或选「都不像」
- 标注者：3 人取多数；标注者画像 = 目标用户的普通听众（不是声乐专业者），另设 5–10 人专业小组做二次校验（看技术维度是否被捕捉）
- 一致性门槛：Cohen's kappa；低于阈值说明问法不稳，改用纯 pairwise 比较式提问
- 「都不像」占比高 → 触发扩库信号，而不是调阈值

### 6.3 指标

1. **Top-1 / Top-3 命中率**：在**被受理**查询上计算（Top-3 含任一标注者多数选中的歌手）
2. **受理率**：必须 ≥ 85%，与 1 一同报告
3. Spearman：仅在有 ≥ 2 位不同首选的 query 上算
4. **跨设备稳定性**：同一人同通道 3 设备，Top-3 重合 ≥ 2/3
5. 拒答质量：另取低质量样本，由 2 人按质量 rubric 标「应拒答」，衡量 precision/recall

### 6.4 反例集

跑调、极小声、嘈杂环境、变声期少年、老年嗓音。不进主指标，用于验证拒答与稳健性。

## 7. 分阶段

| 阶段 | 周期 | 产出 |
|---|---|---|
| 0 地基 | 1–2 周 | 管线同构 + 契约测试；库 v0（10 人）离线特征；冻结底座跑通端到端；库内配对自检 |
| 1 数据与校准 | 3–4 周（与 0 并行启动招募） | 60–100 人真实采集；基准集 v1；Bradley-Terry 校准；第一版 G1 |
| 2 报告 | 2 周 | 四维分位图、Top-3、置信度与拒答、静态可截图页 |
| 3 扩库 | 持续 | 扩到 20–30 人，稳定性复测，评估是否值得微调底座 |

## 8. 风险

- **标注不稳**：人对「像」的判断受熟悉度、性别、曲风支配。缓解：比较式问法、多人多数、kappa 门槛、候选集打乱。
- **修音与混音制造假相似**：含 live 素材 + 两侧对称分离。
- **样本偏差**：男女比例失衡会让女性用户系统性失真。按性别分层建库与分位。
- **Web 采集后处理**：AGC/降噪会毁掉 HNR 与气声比例。缓解：显式关闭 + 单通道验收。
- **歌手侧法务**：先内部分析用途；live 素材来源是阶段 0 的第一个待办。
- **隐私合规**：敏感个人信息，单独同意、最短保留期、可删除。

## 9. 留给构建者的决定

具体模型版本与选型、推理部署形态（CPU/GPU）、前端框架、存储与队列、报告页视觉方案。不影响「准」的目标。

## 10. 需要你拍板的两件事（已按默认写入上文）

1. **是否投入真人采集**（60–100 人、3–4 周）。默认：投入。不投入的话 G1 不成立，只能拿库内留出当代理指标，那就等于在测"歌手识别"，与产品承诺脱节。
2. **歌手素材的合法来源与用途范围**（尤其 live 能否拿到干净母版）。默认：仅内部分析用途、全 studio 也能先跑；live 缺失记为已知偏差。
